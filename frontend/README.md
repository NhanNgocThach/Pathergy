# Pathergy web frontend

The Pathergy frontend is a responsive Next.js application for the features
implemented by the Pathergy API. It uses React, TypeScript, Tailwind CSS,
shadcn-style source components, TanStack Query, React Hook Form, Zod, Vitest,
React Testing Library, and Mock Service Worker.

Pathergy is an educational prototype. Use fictional information only. It does
not provide medical advice, prescribe medication, recommend dosage, or reach a
medication-safety conclusion.

## Architecture

```text
app/                 Next.js App Router pages and layouts
components/          Reusable UI, feedback, health, and layout components
features/            Domain components: auth, profiles, allergies, medication,
                     screening, families, permissions, account, dashboard
hooks/               Small context hooks
lib/                 API client, token store, query keys, formatting, utilities
schemas/             Zod form schemas aligned with backend validation
services/            Typed endpoint calls without backend business logic
types/               TypeScript API response and domain types
i18n/                Dependency-free English, Vietnamese, and Chinese messages
tests/               Vitest/RTL tests and MSW backend mocks
```

Pages call feature components. Features use service functions. Services use the
shared API client. TanStack Query owns server-state caching; query keys include
`patient_id` for health data. Switching profiles removes the previous profile's
cached health queries, and logout clears the complete query cache.

## Routes

Public authentication routes:

- `/login`
- `/register`
- `/verify-email?token=...`
- `/forgot-password`
- `/reset-password?token=...`
- `/auth/verify-email?token=...` and `/auth/reset-password?token=...` compatibility
  routes for development URLs currently generated by FastAPI

Protected routes:

- `/app` — dashboard
- `/my-health` and `/my-health/edit`
- `/allergies`, `/allergies/new`, `/allergies/{id}/edit`
- `/medication-check` and `/medication-check/results?id=...`
- `/screening-history` and `/screening-history/{id}`
- `/families`, `/families/new`, `/families/{id}`
- `/security/sessions`
- `/change-password`
- `/settings`

## Installation and local development

Start FastAPI from the repository root with a configured `.env`:

```dotenv
CORS_ALLOWED_ORIGINS=http://localhost:3000,http://127.0.0.1:3000
AUTH_DEVELOPMENT_MODE=true
AUTH_DEVELOPMENT_BASE_URL=http://localhost:3000
```

Then use another PowerShell window:

```powershell
cd D:\Workspace\Pathergy\frontend
Copy-Item .env.example .env.local
npm install
npm run dev
```

Open <http://localhost:3000>. The only frontend environment variable is:

```dotenv
NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:8000
```

`NEXT_PUBLIC_` values are visible to browsers and must never contain secrets.

## Commands

```powershell
npm run lint

```

Tests mock FastAPI with MSW and never call RxNorm or a live backend. Playwright
is not configured because the current repository has no isolated E2E database
seeding/reset contract. Backend API tests and 59 frontend unit/component tests
cover the current deterministic workflows.

## Backend connection

The frontend uses the existing `/auth`, `/patients`, nested `/allergies`,
`/medications/suggestions`, `/medications/search`, `/medication-check`, `/screening-history`, `/users`, and
`/family-groups` endpoints. It normalizes both backend error formats:

```json
{"detail":{"code":"FAMILY_PERMISSION_DENIED","message":"..."}}
```

and plain FastAPI string/list `detail` responses. Network failures and malformed
successful responses become typed frontend errors. No internal stack trace is
displayed.

The medication textbox calls `/medications/suggestions` only after two
characters and a 350 ms debounce. The ARIA combobox supports mouse selection,
Arrow Up/Down, Enter, and Escape. Its requests are cancelled when a newer query
replaces them. Suggestion failures do not block manual medication search and
selecting a suggestion never starts allergy screening automatically.

## Vercel deployment

Import the Pathergy GitHub repository in Vercel, set the project root directory
to `frontend`, and set `NEXT_PUBLIC_API_BASE_URL` to the public Render API origin.
No Vercel configuration file is required. This public variable is embedded at
build time and must never contain backend or database secrets. Full Neon,
Render, CORS, authentication, and automatic deployment instructions are in
[`docs/DEPLOYMENT.md`](../docs/DEPLOYMENT.md).

## Authentication and refresh flow

1. Registration creates an account and personal patient profile; it does not log
   the user in.
2. The user consumes the verification token and then logs in.
3. The access token is kept only in JavaScript memory.
4. The opaque refresh token is kept in `sessionStorage` for the browser tab.
5. Protected requests receive `Authorization: Bearer ...`.
6. An eligible access-token `401` starts one shared refresh operation. Concurrent
   failures wait for the same operation.
7. The rotated token pair replaces the old pair and the original request retries
   once. Credential errors do not trigger rotation.
8. Failed refresh clears tokens and cached health data. The route guard returns
   the user to login without an infinite retry loop.

Password reset and password change revoke every backend session. Logout clears
local credentials even if the network logout call fails. Route guards improve
navigation, but backend authentication and authorization remain the security
boundary.

## Profiles and family permissions

The profile selector begins with the user's personal profile and includes
profiles discoverable through `GET /patients`. When available, it adds the family
name and relationship from active family membership data. It never mixes query
keys between patient IDs.

Family role and health-data permission are displayed separately:

- `OWNER` and `ADMIN` manage group/member records.
- Those roles do not automatically access another adult member's health data.
- Only `BASIC_PROFILE`, `ALLERGIES`, and `SCREENING_HISTORY` appear in the UI,
  because those are the permission types currently enforced by health routes.
- Users edit only their own active membership's sharing choices.
- A family medication check requires allergy view and screening-history edit
  permission in the same active family membership.

Member responses contain IDs but not names or emails, so the interface uses
labels such as `User #2`. Adding a member accepts only an existing numeric user
ID and begins as `PENDING`; there is no invitation workflow.

## Medication-safety wording

Screening displays only the backend categories:

- `POTENTIAL_ALLERGY_MATCH`
- `NO_RECORDED_MATCH_FOUND`
- `UNABLE_TO_VERIFY`

Potential matches show recorded and standardized ingredients plus the match
method. A no-recorded-match result explicitly says that it does not confirm
medication safety. Unable-to-verify makes no medical conclusion. Every result
keeps the educational/professional-review disclaimer. Warning meaning is
communicated with icons, headings, text, and styling rather than color alone.

## Accessibility and responsive design

- Persistent labels, semantic headings, lists, tables, dialogs, and landmarks.
- Keyboard-accessible forms and dialogs with visible focus rings.
- Skip-navigation link and `aria-current` navigation state.
- Polite live regions for async checks and notifications.
- Status words/icons accompany color.
- Minimum 44px controls and reduced-motion support.
- Desktop sidebar, mobile bottom navigation and mobile “More” dialog.
- Allergy rows transform to cards on small screens; other tables scroll safely.

## Languages

The shared interface includes English, Vietnamese, and Simplified Chinese. The
selector appears on public authentication screens and in the protected desktop
and mobile shells. The choice is stored in browser `localStorage`, and the page
language attribute updates for assistive technology. English remains the
fallback when a message has not yet been translated; backend validation and
third-party RxNorm messages are not rewritten by the browser.

## Browser security headers

Next.js sends anti-framing, MIME-sniffing, referrer, and browser-capability
headers on every route. Production additionally sends HSTS and a restrictive
Content Security Policy that permits API connections only to the deployed
Pathergy API. These headers reduce common browser attacks but do not replace
backend authorization or hosting-provider DDoS protection.

## Current backend-driven limitations

- The API returns refresh tokens as JSON rather than HttpOnly cookies.
  `sessionStorage` therefore remains vulnerable if an XSS flaw is introduced.
- Screening history has no detail endpoint and does not persist ingredients,
  matches, or result messages. The detail page shows only stored list fields.
- Session listing returns active sessions only. Revoked sessions cannot be shown,
  and “revoke all” includes the current session.
- Account email and display name cannot be edited.
- Shared profile responses have no capability metadata; a denied mutation is
  handled as `FAMILY_PERMISSION_DENIED`.
- Family members cannot be searched by name/email and membership responses do
  not contain safe display names.
- No server-side history filtering or pagination exists.
- Development verification/reset URLs must be disabled outside local work.

## Intentionally not implemented

QR/email invitations, phone/SMS login, passkeys, biometrics, OAuth, MFA, doctor
accounts, prescription issuing, documents, notifications, nutrition, drug
interactions, AI, FHIR, AWS deployment, a native mobile application, dark mode,
and unsupported account/family actions remain outside this frontend.

## Manual test checklist

1. Register with fictional data, open the development verification link, and log
   in.
2. Confirm `/app` redirects to login after tokens are cleared.
3. View and edit the personal profile.
4. Add, edit, and delete a fictional allergy; try a duplicate substance.
5. Search a fictional medication name and inspect RxNorm ingredients.
6. Run a medication check and verify one of the three conservative result panels.
7. Open history and confirm its detail page shows only stored fields.
8. Create a family, add an existing fictional user ID, activate the pending
   membership, change role/relationship, and test final-owner protection.
9. Change only your own three enforced sharing permissions.
10. Switch profiles and confirm the visible health data reloads for that person.
11. Revoke a non-current session, then revoke the current/all sessions.
12. Repeat major flows using keyboard only and at a narrow mobile viewport.
